## 1. 先理解游戏：设计拆解

### 1.1 一句话概括

> 你是一团「灰烬」，在随机生成的地牢里往下走；你的**血量就是背包里球（Orb）的数量**，背包最上面那颗球既是你的武器，也是你下一口会被打掉的血；走到楼梯、召唤并击杀 Boss，就能进入下一层，一共三层。

### 1.2 核心循环

```
        ┌─────────────────────────────────────────────┐
        │                                             │
        ▼                                             │
  探索地牢（移动 / 视野 / 躲怪）                        │
        │                                             │
        ▼                                             │
  捡球 → 背包变长 = 血量变多 / 栈顶换武器               │
        │                                             │
        ▼                                             │
  走到楼梯（Downstairs）                               │
        │                                             │
        ▼                                             │
  召唤 Boss（过场画面）                                 │
        │                                             │
        ▼                                             │
  击杀 Boss ──成功──► 存档 → 下一层 ───────────────────┘
        │
        └──失败（HP 归零）──► 死亡结算
```

这个循环里包含了肉鸽（Roguelike）的标准四要素：**随机生成、永久死亡、回合制、资源取舍**。本项目还额外加了两条：

- **三层递进**：每层 Boss 不同（Tower Gargoyle → Ghoul → Giovanni）；
- **确定性随机**：同一个种子（Seed）永远生成同一张地图、同一批敌人。

### 1.3 三个「反常识」的设计（也是最值得学的部分）

#### 设计一：血量 = 背包栈长度

普通游戏里「血量」是一个独立数字。这里不是：

- `Inventory` 是一个数组，**数组长度就是 HP**；
- 受伤时从**栈尾**弹出 N 个球（`pcTakeDamage` → `removeItem(damage)`）；
- 只有当 `damage > 数组长度` 时才会死 —— 也就是说 **0 HP 仍然活着**，只是背包空了、没有武器了。

代码位置：[GameSystem.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/system/GameSystem.ts#L298-L304)、[Components.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/ecs/Components.ts#L153-L224)。

设计意图与代价：

| 意图 | 代价 |
| --- | --- |
| 把「血量」和「技能栏」合并，让每一颗球都是「血 + 武器」的双重身份 | 挨打不仅掉血，还会**把武器打掉**，负反馈很重 |
| 栈是 LIFO（后进先出），栈顶是当前武器 | 想换武器就得先把上面的球用掉/被打掉，操作不自由 |
| 长度即血量，天然形成「越强越脆/越弱越肉」的张力 | 玩家很难直观理解「我现在到底还能挨几下」 |

> **给设计新手的提醒**：这是一个很有创意、但对新手玩家不友好的机制。你可以学它的「资源即生命」思路，但第一版建议把 HP 和技能栏分开，先保证可玩性。

#### 设计二：按键是「上下文相关」的

同一个 `Space` 在不同状态下做不同的事：

| 当前状态 | 按 Space 的效果 |
| --- | --- |
| 站在楼梯上 | 下楼 / 召唤 Boss |
| 站在球上且背包没满 | 捡球 |
| 背包栈顶不是 armor | 进入瞄准（aim）模式 |
| 瞄准模式中 | 确认施放 |

实现方式是「屏幕（Screen）+ 模式（Mode）」：`main` 屏幕有三个模式 `main / examine / aim`，每次按键先问当前屏幕 `getAction(e, mode)` 映射成动作名，再分派。

代码位置：[Screens.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/screens/Screens.ts#L11-L18)、[GameSystem.pcPickOrUse](file:///d:/work2/test_funplay_mcp/assets/scripts/system/GameSystem.ts#L306-L325)、[KeyInput.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/input/KeyInput.ts#L10-L78)。

#### 设计三：随机是「确定的」

所有随机都走 `RotRng`（Alea 算法），**禁止 `Math.random()`**。同一个种子：

- 地图完全一样；
- 敌人数量/种类/位置完全一样（因为 RNG 调用顺序固定）；
- 掉落完全一样。

这带来两个好处：**可复现的 bug**、**可对比的回归测试**（改一行代码后跑同一个种子，看地图是否变化）。代价是：**任何「顺手改一下调用顺序」都会让整张地图变掉**，所以源工程把「RNG 调用次数与顺序」列成了硬约束。

代码位置：[RotRng.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/vendor/RotRng.ts)、[GameSystem.startRNG](file:///d:/work2/test_funplay_mcp/assets/scripts/system/GameSystem.ts#L1048-L1064)、[EntityRegistry.dungeon](file:///d:/work2/test_funplay_mcp/assets/scripts/ecs/EntityRegistry.ts#L23-L87)。

### 1.4 机制速查表

#### 球（Orb）

| 球 | 作用 | 攻击射程 | 备注 |
| --- | --- | --- | --- |
| `slime` | 传送到瞄准点（无视墙体） | 2 | 位移技 |
| `fire` | 火焰攻击 | 1 | 掉落率最高 |

#### Boss 流程

1. 站在楼梯上按 Space（Boss 状态 `inactive`）→ 过场；
2. `placeBoss(downstairs, pc, 2)` 在楼梯附近、距玩家 2 格以外找位置；
3. 按层数召唤 `gargoyle / ghoul / giovanni`，加入调度器（延迟 2 回合行动）；
4. Boss 死亡判定 `bossIsDead`：L1 必须 gargoyle **和** juvenileGargoyle **全部**死亡才算赢；
5. 赢了且不是第 3 层 → 写存档、提示「Game saved.」→ 关掉标签页重开即下一层。

### 1.5 这个设计为什么「难」

这不是 bug，是设计结构决定的：

1. **挨打 = 掉血 + 掉武器**。普通游戏挨打只掉血，这里栈顶武器会一起没；
2. **玩家 1 伤，敌人 2 伤**。换血永远亏；
3. **敌人 8 向移动，玩家 4 向**。斜角是敌人的优势方向；
4. **Boss 实际血量是 7 点**（5 + 2），理想 6 HP 每口只吃 1 伤刚好 0 HP 险胜，容错为 0；
5. **随机生成的地图可能把你围死**，而你没有位移以外的逃生手段（slime 是初始球之一）。

> 这解释了 [游玩体验与难度评估](file:///d:/work2/test_funplay_mcp/doc/游玩体验与难度评估.md) 里「10 局 0 通关」的结果：不是机器人不会玩，是这套数值本身把容错压到了接近 0。

## 2. 从设计到代码：一次按键的完整旅程

### 2.1 分层结构（依赖只能向下）

```
core        MainGame.ts            全局命名空间 Main（版本、颜色、实体表）
  │
vendor      RotRng / RotCellular / RotFov / RotScheduler   与引擎无关的算法库
  │
ecs         Components / EntityFactory / EntityRegistry     组件、实体工厂、实体模板
  │
system      GameSystem / MonsterAI / AchievementSystem      游戏规则
  │
screens     ScreenFactory / Screens                        画面与按键分派
  │
input / data / save                                         键盘、文案、存档
  │
GameRoot.ts                                                唯一入口（等价 window.onload）
```

**为什么这么分**：`vendor / ecs / core` 不 `import 'cc'`，所以它们能脱离 Cocos 在 Node 里直接跑。这正是本项目能用 headless 回放做验收的根本原因（第 6 章）。

### 2.3 启动时发生什么

启动分两段：`GameRoot._boot()`（[GameRoot.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/GameRoot.ts#L48-L109)）先把「屏幕、文案、存储、输入」准备好；随后进入 `main` 屏幕时，`Screens.main.initialize()`（[Screens.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/screens/Screens.ts#L18-L106)）才真正生成这一局的世界。代码里 `[boot] 1/9 … 9/9` 的日志，就是这两段穿插打印出来的：

| 日志 | 在哪 | 做什么 |
| --- | --- | --- |
| 1/9 | `_boot` | 建 `GridRoot` + `GridRenderer`，挂到 `Main.display` |
| 2/9 | `main.initialize` | 建 `Seed`，`startRNG()`（读存档种子或开发种子） |
| 3/9 | `main.initialize` | 建 `Timer`，`engine.start()`（回合泵开始待命） |
| 4/9 | `main.initialize` | 建 `Dungeon`（生成地图）与 `marker` |
| 5/9 | `main.initialize` | 建 `PC`、填充初始背包、放到随机地板格 |
| 6/9 | `main.initialize` | `createEnemies()`（25～29 只），记录敌人组成 |
| 7/9 | `main.initialize` | 放精英/普通怪、楼梯、球 |
| 8/9 | `main.initialize` | 打印生成日志、删除上一局存档 |
| 9/9 | `_boot` | 安装键盘，进入 `main` 或 `cutScene` |

`_boot` 在这些步骤之间还做了三件事：读开发模式、初始化文案与全局实体、检查 `localStorage`（不可用就直接在屏幕上报错并 `return`）。

顺序不能换，原因很直接：

- 没有 `display`，后面任何报错都没地方画；
- 没有 `Seed` 和 RNG，地图无从生成；
- 没有 `Timer`，PC 就算加进调度器也不会行动；
- 键盘必须在进入屏幕前装好，否则第一屏按不动。

外层还有 `try/catch` 兜底：初始化任何一步异常，都会把错误画到屏幕上并写 `lastBootError`，避免「黑屏无提示」。

### 2.4 每帧发生什么（`update()`）

[GameRoot.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/GameRoot.ts#L111-L124)：

```ts
protected update(): void {
    if (!this._renderer) { return; }

    // 1) 分帧创建 1820 个 Label，没建完就这一帧什么都不画
    if (!this._renderer.stepCreate()) { return; }

    // 2) 回合泵只置了脏标记，这里每帧统一重绘一次
    if (Main._pendingRedraw) {
        Main._pendingRedraw = false;
        Main.display.clear();
        Main.screens.main.display();
    }

    // 3) 真正把字符缓冲刷到 Label 上
    if (this._renderer.dirty) {
        this._renderer.flush();
    }
}
```

这三段是理解整个渲染的关键：

- **业务层从不直接碰 `Label`**，只往字符缓冲里 `draw()`；
- **重绘被合并成每帧一次**，即使一个回合里 NPC 动了 20 步，也只画一次；
- **首帧分帧创建**，避免同步建 1820 个节点把页面卡死几秒。

### 2.6 回合调度：`lock / unlock` 到底在做什么

这是新手最容易晕的地方。用一句话解释：

> **谁「正在行动 / 正在等玩家思考」，谁就持有锁；锁计数为 0 时，引擎就一直推进下一个角色，直到有人重新上锁。**

时序（简化）：

| 时刻 | `_lock` | 谁在动 | 发生什么 |
| --- | --- | --- | --- |
| 启动 | 1 → 0 | PC | `engine.start()` 解锁，泵开始；轮到 PC，`pcAct` 上锁到 1，等按键 |
| 玩家按键 | 1 → 0 | — | `move()` 解锁，泵开始 |
| 泵第 1 步 | 0 → 1 → 0 | NPC A | NPC 上锁 1，走一步，`unlockEngine(1.2)` 解锁回 0 |
| 泵第 2 步 | 0 → 1 → 0 | NPC B | 同上 |
| … | | | 直到调度器再次轮到 PC |
| 轮到 PC | 0 → 1 | PC | `pcAct` 上锁为 1，泵退出（`_lock !== 0`），等下一次按键 |

**「速度」就是这个 `duration`**：`scheduler.setDuration(1.2)` 表示这个角色下次行动要等 1.2 个时间单位。于是：

| 行为 | duration | 效果 |
| --- | --- | --- |
| 普通移动/攻击 | 1 | 一回合一次 |
| `slowMove` 1.2 / zombie 1.5 | >1 | 慢，玩家能多走几步 |
| `fastMove` 0.5（raven）/ `fastAttack` 0.4（ghoul） | <1 | 快，一回合能行动多次 |

代码：[ActionDuration 组件](file:///d:/work2/test_funplay_mcp/assets/scripts/ecs/Components.ts#L139-L151)、[EventQueue](file:///d:/work2/test_funplay_mcp/assets/scripts/vendor/RotScheduler.ts#L5-L65)。

**兜底**（规则第 4 节要求）：`_lock < 0` 视为计数失配，立即重置为 1 并报错；单次泵最多 2000 步，超限强制把控制权还给玩家。没有这两条，一个 AI 的死循环就会让整个游戏「按键永久无反应」。

### 2.7 渲染旅程

```
screens.main.display()  →  Main.display.draw(x, y, ch, fg, bg)  写字符缓冲
                            │

GameRoot.update()        →  display.flush()  只更新「和上次不一样」的格子
```

## 3. 实现里程碑：照着做一遍

下面是把「一个空 Cocos 工程」做到「能跑的 ASCII 肉鸽」的顺序。**每一阶段都必须能单独验证**，不要跳步 —— 这是本项目能稳定推进的核心方法。

| 阶段 | 目标 | 关键产物 | 验收标准 |
| --- | --- | --- | --- |
| M0 骨架 | 工程能启动、能打日志 | `GameRoot.ts` + 场景 | 浏览器控制台出现启动日志 |
| M1 字符屏 | 把屏幕抽象成 70×26 字符缓冲 | `GridRenderer` | 能在指定坐标画 `@` 和文字 |
| M2 地图与随机 | 同种子同地图 | `RotRng` + `RotCellular` + `Dungeon` | 固定种子两次生成完全一致 |
| M3 实体 | 玩家/怪/球都是「组件拼装」 | `Components` + `EntityFactory` + `EntityRegistry` | 能创建 PC 并读到 HP/位置 |
| M4 回合调度 | 玩家动一步，怪才动 | `RotScheduler` + `ActionDuration` | 玩家不动，怪不动 |
| M5 视野 | 只显示看得见的格子 | `RotFov` + `pcRememberTerrain` | 墙后不可见，走过的地方变暗 |
| M6 输入 | 按键 → 动作名 → 系统函数 | `KeyInput` + `Screens.keyInput` | `h/j/k/l` 四向移动，方向键也行 |
| M7 战斗与拾取 | 撞怪攻击、站球上捡球 | `pcAttack` / `pcPickOrUse` | 攻击掉血、死亡掉落、捡球变长 |
| M8 AI | 怪会追、会打、会跑 | `MonsterAI` | 怪能绕墙接近，射程内会攻击 |
| M9 屏幕与文案 | 主界面/过场/帮助/成就 | `Screens` + `TextData` + `ScreenLayout` | 状态栏显示 HP/背包/敌人 |
| M10 存档 | 关掉再开还能继续 | `SaveSystem` 六键 | 刷新浏览器后关卡/背包还在 |
| M11 headless 验证 | 不开编辑器也能跑逻辑 | `temp/gen-test/headless` | `node run.js` 打印 26 行 ASCII |
| M12 兜底与打磨 | 不卡死、不黑屏 | 循环上限、启动异常兜底 | 连续玩 10 局无卡死 |

### M0：最小可启动骨架

**做什么**：一个场景（`Canvas → Camera + GameRoot`），`GameRoot` 挂一个脚本，`onLoad` 里 `console.log('[boot] ok')`。
**为什么先做这个**：先确认「引擎 → 脚本 → 浏览器」这条链路是通的，再去写游戏逻辑。链路不通时写再多逻辑也看不到。
**坑**：脚本没被场景引用、脚本编译报错，表现都是「什么都不发生」。所以启动日志要打在 `onLoad` 第一行。

### M1：字符屏

**做什么**：一个 `GridRenderer`，内部维护 `_ch/_fg/_bg` 三个数组（长度 1820），对外只有 `draw / drawText / clear / flush`。
**关键决策**：

- 坐标系用「字符格」，业务层永远写 `draw(3, 5, '@')`，不碰像素；
- 一个格子一个 `Label`，而不是一个 `RichText` 拼整屏 —— 后者改一个字要重新排版，差分刷新无从谈起；
- 每格 `cacheMode = CHAR`，让引擎缓存字形，减少 draw call。

**验收**：`draw(1,1,'@')` 出现在左上角第 2 格；`flush()` 后只有变化的格子更新。

### M2：地图与确定性随机

**做什么**：`RotCellular`（元胞自动机）生成洞穴，`connect()` 打通孤岛，`Dungeon` 组件存 `terrain` 与 `memory`。
**关键决策**：

- 种子先写进 `Seed` 实体，再 `RotRng.setSeed()`；
- 生成循环必须有上限（本项目 `MAX_CYCLE = 60`，超限取最接近 60% 面积的一版并 `console.warn`）；
- 地板率目标 60%，太高全是空地、太低走不通。

**验收**：`#12345` 连续跑两次，26 行 ASCII 完全一致。

### M3：实体与组件

**做什么**：`Factory` + 组件。玩家 = `Position + Display('@') + ActionDuration + Inventory(6) + Damage(1) + DropRate + AttackRange + FastMove + CombatRole`。
**为什么用组合而不是继承**：

- 怪和玩家共享「位置/血量/攻击范围/移动速度」这些组件；
- 加一个新怪 = 在 `EntityRegistry` 里拼一组组件 + 指定 `act` 函数，不用改类继承树；
- 这也是 ECS 思想的最小可用版本（严格 ECS 会把数据与行为再拆开，本项目为了 1:1 移植保留了「实体挂 act」的写法）。

**验收**：`Main.entity.pc()` 后能 `getEntity('pc').Inventory.getLength() === 5`（初始 5 颗球）。

### M4：回合调度

**做什么**：`EventQueue`（按时间排序）+ `RotScheduler`（重复调度）+ `TurnEngine`（同步泵）。
**关键决策**：

- **不用 `setInterval`/`setTimeout`**。浏览器定时器不可暂停、不可复现，而且一次按键里要推进很多步；
- 用**同步 while 泵**：玩家解锁后，一口气把该动的 NPC 全部推进完，再回到玩家；
- 每个 act 开头 `lock()`、结束 `unlock()`，用计数保证「嵌套解锁」不会重复泵。

**验收**：玩家不动时怪不动；玩家走一步后，速度快的 raven 可能已经走了两步。

### M5：视野

**做什么**：`RotFov`（PreciseShadowcasting）+ `pcRememberTerrain()`：看得见的格子写亮色，看过的格子写暗色，没看过的画黑。
**验收**：贴墙走一圈，墙后的怪不显示；走过的走廊保留地形但怪物消失。

### M6：输入

**做什么**：`Main.input.keybind` 三张表（fixed / move / fastMove / interact），`getAction(e, mode)` 反查动作名；`toKeyString()` 把 Cocos `KeyCode` 归一化成 `'h' / 'ArrowLeft' / ' '`。
**关键决策**：

- **业务层永远拿字符键名**，不拿数字 KeyCode；
- **Shift 自己跟踪**（`KEY_DOWN` 里记 16/2000，`KEY_UP` 清掉），因为 `EventKeyboard` 不告诉你修饰键状态；
- 每个屏幕注册自己的 `keyInput`，`listenEvent('add', 'main')` 切换。

**验收**：`h/j/k/l`、方向键、`Shift+H` 快速移动、`Space`、`Escape` 都符合预期。

### M7：战斗与拾取

**做什么**：`move()` 发现目标格有怪 → `pcAttack`；`Space` → `pcPickOrUse` 的三段判断；`pcTakeDamage` 从栈尾弹球。
**关键决策**：

- 「使用球」不消耗球，所以武器可以反复用；
- 掉落率按「击杀时栈顶是什么球」决定（`DropRate`），所以「用什么杀」影响收益；
- 死亡判定是 `damage > length`，不是 `length === 0`。

**验收**：打一只 rat 掉球；捡球后 HP 条变长；被狗咬一口后栈顶武器消失。

### M8：AI

**做什么**：`npcDecideNextStep` 取周围 8 格（含原地），过滤非法格，按「更近 / 等距 / 更远」分三档候选，`RotRng` 随机挑一个。
**关键决策**：

- 8 向而不是 4 向：斜角追击更自然，也更危险；
- 「谨慎型」敌人（`CombatRole.cautious`，如 archer）不主动贴身，保持射程；
- 每个怪的 `act` 是一个大 `if/else` 链（看不见 → 搜索；在射程内 → 攻击；否则 → 接近），这就是「行为树」的朴素写法。

**验收**：隔着墙的怪会绕过来；archer 停在 3 格外射你。

### M9：屏幕与文案

**做什么**：`ScreenLayout` 只存坐标（`canvas 70×26`，`status 13 宽`，`message 5 高`……），`Screens` 按固定顺序绘制，`TextData` 集中所有文案。
**为什么坐标要单独一层**：UI 调整是高频操作，把魔法数字散落在绘制函数里，改一次要翻十个文件。

**验收**：主界面能同时显示版本号、层数、HP、背包、敌人列表、种子、底部消息。

### M10：存档

**做什么**：`SaveSystem` 封装 `sys.localStorage`，固定六个键：`achievement / wizard / dungeonLevel / seed / inventory / orb`。
**关键决策**：

- 只允许这一处碰 localStorage；
- 读失败静默降级（`storageAvailable()` 为 false 时屏幕提示），不能抛出中断启动；
- 地面上的球最多存 4 个（按 lump/fire/ice/slime 顺序）。

**验收**：过完 L1 存档后刷新页面，仍在 L2 且背包一致。

### M11：headless 验证

**做什么**：一个 `cc` 替身（Node/Label/input 的空实现）+ `run.js`，真实执行 `GameRoot.onLoad()`，把字符缓冲直接打印成 26 行文本。
**为什么值得做**：

- 不需要开编辑器、不需要浏览器，秒级回归；
- 逻辑错误（死循环、RNG 顺序、坐标越界）能在文本里直接看见；
- 后续「自动游玩 10 局」就是在这个基础上加一个按键注入 + 寻路机器人（见 `play-one.js`）。

**验收**：`node run.js` 输出过场 → 主界面 → 按 `l` 后 PC 位置变化。

### M12：兜底与打磨

**做什么**：所有循环加硬上限、启动异常打到屏幕、锁计数自愈、重绘合并。
**为什么最后做**：兜底是「防猝死」，但前提是先有一个能跑的核心。没有核心就加兜底，只会在错误的地方打补丁。

### 本项目真实走过的弯路（比里程碑更有价值）

里程碑是「理想顺序」，真实施工一定会有返工。本项目踩过的五个坑，每一个都对应一条后来写进规则的做法：

| 现象 | 根因 | 最终做法 |
| --- | --- | --- |
| 打开后白屏数秒 | 同步创建 1820 个 `Label` | 分帧创建 + 每帧合并重绘 |
| 按键永久无反应 | 回合泵 `lock/unlock` 计数失配（可为负） | `_lock < 0` 自愈 + 单次泵上限 2000 步 |
| 地牢偶尔生成很久 | `do-while` 没有上限 | `MAX_CYCLE = 60` + 取最接近目标的一版兜底 |
| 逻辑无法自动验证 | 业务层直接 `import 'cc'` | 把 `cc` 限制在 render / input / save / 入口四处 |
| 误判「游戏没在跑」 | 截 Creator 编辑器窗口（预览其实在浏览器里） | 查 `running` + 探端口 + 看浏览器控制台 |

这五条后来被固化成硬规则（循环上限、依赖方向、验证 SOP），也是 [移植执行方案第 14 章](file:///d:/work2/test_funplay_mcp/doc/cursedSouls_CocosCreator_移植执行方案.md) 的来源。

## 4. Cocos Creator 零基础最小知识

### 4.1 编辑器四个区域

| 区域 | 作用 | 本项目里你要关心的 |
| --- | --- | --- |
| **Hierarchy（层级）** | 场景里的节点树 | 只有 `Canvas → Camera + GameRoot` |
| **Scene（场景视图）** | 可视化摆放 | 基本不看，游戏画面全是代码画的 |
| **Inspector（属性）** | 选中节点的组件与属性 | Canvas 的 `UITransform` 1280×720 |
| **Assets（资源）** | 脚本、场景、图片 | `assets/scripts`、`assets/scene.scene` |

底部还有 **Console**（日志）和 **Preview**（预览）。调试 90% 的时间在这两个地方。

### 4.2 四个概念

- **场景（Scene）**：一个关卡/界面的容器。本项目只有一个 `scene.scene`；
- **节点（Node）**：场景树上的一个对象，有位置、缩放、层级；
- **组件（Component）**：挂在节点上的功能模块。`Label`（文字）、`UITransform`（尺寸与锚点）、`Graphics`（画矩形）都是组件；
- **资源（Asset）**：脚本、场景、图片、字体等文件。

**关键区别**：Cocos 的「组件」和本项目的「ECS 组件」是两回事。前者是引擎的 `Component`（挂在 Node 上），后者是普通 TS 类（挂在实体对象上）。本项目只有 `GameRoot` 和 `GridRenderer` 用引擎组件，游戏实体全是普通对象。

### 4.3 坐标系（最容易踩的坑）

Cocos 的 UI 坐标：**原点在父节点中心，y 轴向上为正**。
字符网格的坐标：**原点在左上角，y 轴向下为正**。

本项目用一次转换解决：

```ts
// Canvas 中心为原点；GridRoot 锚点设在左上，再左移半宽、上移半高
gridTransform.setAnchorPoint(0, 1);
gridTransform.setContentSize(1120, 572);   // 70*16, 26*22
gridRoot.setPosition(-560, 286);
```

之后每个格子：

```ts
node.setPosition(
    x * CELL_WIDTH + CELL_WIDTH / 2,
    -(y * CELL_HEIGHT + CELL_HEIGHT / 2)   // 注意负号
);
```

代码：[GameRoot.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/GameRoot.ts#L48-L70)、[GridRenderer.stepCreate](file:///d:/work2/test_funplay_mcp/assets/scripts/render/GridRenderer.ts#L85-L130)。

**记忆法**：引擎里「往上」是 y 变大；网格里「往下」是 y 变大。两者相反，所以网格 y 转像素时要加负号。

### 4.4 本项目只用到的引擎 API

| API | 用途 | 出现位置 |
| --- | --- | --- |
| `Node` | 建节点 | GameRoot、GridRenderer |
| `UITransform` | 尺寸 + 锚点 | 同上 |
| `Label` | 一个字符格 | GridRenderer |
| `Graphics` | 画背景色块 | GridRenderer |
| `input.on(KEY_DOWN/KEY_UP)` | 键盘 | KeyInput |
| `sys.localStorage` | 存档 | SaveSystem |
| `Component.onLoad / update` | 生命周期 | GameRoot |
| `game.canvas.focus()` | 预览时抢焦点 | KeyInput |

**没有用到**：物理、动画、Spine、3D、UI 布局系统、预制体。所以这个项目的 Cocos 学习成本其实很低 —— 你只需要理解「节点 + 组件 + 生命周期 + 输入 + 每帧更新」。

### 4.5 十分钟做出第一个可玩的东西（练手）

1. 新建 2D 场景，确认 Canvas 设计分辨率 1280×720；
2. 在 Canvas 下建空节点 `Player`，加 `UITransform`（40×40）；
3. 在 `Player` 下建子节点 `Label`，内容 `@`，字号 40；
4. 新建脚本 `Player.ts`，挂到 `Player` 上：

```ts
import { _decorator, Component, input, Input, EventKeyboard, Label } from 'cc';
const { ccclass } = _decorator;

@ccclass('Player')
export class Player extends Component {
    private _x = 0;
    private _y = 0;

    onLoad() {
        input.on(Input.EventType.KEY_DOWN, this._onKey, this);
    }

    private _onKey(e: EventKeyboard) {
        // 37/38/39/40 = 左/上/右/下
        if (e.keyCode === 37) { this._x -= 40; }
        if (e.keyCode === 39) { this._x += 40; }
        if (e.keyCode === 38) { this._y += 40; }
        if (e.keyCode === 40) { this._y -= 40; }
        this.node.setPosition(this._x, this._y);
    }
}
```

5. 点预览 → 在浏览器里用方向键移动 `@`。

**这一步的验收**：你能独立回答「为什么 y 用 += 是往上？」「为什么监听要写在 `onLoad` 而不是 `update`？」。答不上就再试一次，这两个问题是后面所有坐标/输入代码的地基。

### 4.6 预览与构建

- 关闭标签页 = 预览会话结束，端口不再监听，需要重新点预览；
- 构建：项目 → 构建发布，选 Web Mobile/Web Desktop。

### 4.7 新手最容易踩的 6 个坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |

## 5. 八个关键技术点

### 5.1 1820 个 Label 的分帧创建 + 差分刷新

**问题**：一次 `new Node + addComponent(Label)` 1820 次，主线程会卡住数秒，表现为「打开就白屏」。
**做法**：

- `stepCreate(budget = 200)` 每帧只建 200 个，建完前 `update()` 直接 return；
- 每个格子缓存「上次渲染值 `_rch/_rfg`」，`flush()` 只更新变化的格子；
- 背景色用一张 `Graphics` 重画，而不是每格一个 Sprite。

代码：[GridRenderer.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/render/GridRenderer.ts#L85-L130)、[flush](file:///d:/work2/test_funplay_mcp/assets/scripts/render/GridRenderer.ts#L227-L249)。

### 5.2 字符坐标 → 像素坐标

**问题**：游戏逻辑只想说「第 3 列第 5 行」，渲染要知道像素。
**做法**：所有换算是 `x * 16 + 8`、`-(y * 22 + 11)`，且只出现在 `GridRenderer.stepCreate` 一处。
**好处**：换分辨率/字号时只改常量，业务代码零改动。

### 5.3 键盘归一化 + Shift 跟踪

**问题**：Cocos 给的是 `KeyCode` 数字，源工程逻辑用的是字符 `'h'`、`'ArrowLeft'`、`' '`；而且 `EventKeyboard` 不提供 `shiftKey`。
**做法**：

- `toKeyString()` 一张 switch 表，把 37/38/39/40/32/27/65-90 等翻成字符；
- 自己在 `KEY_DOWN` 记 Shift（左 16、右 2000），`KEY_UP` 清掉；
- 之后业务层永远只见到 `{ key, shiftKey }`。

代码：[KeyInput.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/input/KeyInput.ts#L102-L184)。

### 5.4 回合泵 `lock / unlock`

**问题**：回合制需要「玩家按键 → 所有该动的怪依次行动 → 回到玩家」，而浏览器事件是异步的。
**做法**：同步 while 泵 + 锁计数（见 2.6）。
**兜底**：`_lock < 0` 自愈、单次最多 2000 步。

代码：[TurnEngine.unlock](file:///d:/work2/test_funplay_mcp/assets/scripts/vendor/RotScheduler.ts#L156-L190)。

### 5.5 8 向 AI 决策

**问题**：怪要会追、会跑、会保持距离，还要有点随机性（不然一群怪走成一条线）。
**做法**（`npcDecideNextStep`）：

1. 取周围 3×3（含原地）；
2. 过滤掉墙、其他怪、玩家所在格；
3. 算每格到玩家的距离；
4. 按意图分三档：`moveClose`（更近优先）、`moveAway`（更远优先）、`keepDistance`（等距优先）；
5. 在候选里用 `RotRng` 随机挑一个 —— 这一步同时消耗了随机数，**不能随手删**。

代码：[MonsterAI.npcDecideNextStep](file:///d:/work2/test_funplay_mcp/assets/scripts/system/MonsterAI.ts#L154-L270)。

### 5.6 确定性随机（Alea）

**问题**：`Math.random()` 不可复现，bug 无法回放。
**做法**：`RotRng` 实现 Alea，`setSeed(seed)` 后每次 `getUniform()` 推进内部状态；所有生成逻辑（地图、敌人、掉落、AI 选择）都从它取数。
**纪律**：**不新增、不删除、不调换任何 `getUniform()` 调用**，否则同种子地图立刻变样。

代码：[RotRng.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/vendor/RotRng.ts)、[GameSystem.startRNG](file:///d:/work2/test_funplay_mcp/assets/scripts/system/GameSystem.ts#L1048-L1064)。

### 5.7 六键存档

**问题**：关掉浏览器再打开要能续玩，但存档点不能太碎（否则玩家可以随时 SL 大法）。
**做法**：只在「Boss 战胜利 + 下楼」时存一次，固定六个键：

| 键 | 内容 |
| --- | --- |
| `achievement` | 成就解锁状态 |
| `wizard` | 开发者模式开关 |
| `dungeonLevel` | 当前层 |
| `seed` | 本局种子 |
| `inventory` | 背包数组 |
| `orb` | 地面上的球（最多 4 个） |

代码：[SaveSystem.ts](file:///d:/work2/test_funplay_mcp/assets/scripts/save/SaveSystem.ts)、[pcUseDownstairs](file:///d:/work2/test_funplay_mcp/assets/scripts/system/GameSystem.ts#L375-L391)。

### 5.8 文本内联颜色 + 自动断行

**问题**：ASCII UI 需要「一句话里几个词不同颜色」，还要在固定宽度内换行。
**做法**：`drawText` 先把 `%c{red}` / `%b{...}` 切成 token，按宽度断行（优先在空格处断），再逐字 `draw`。断行循环有硬上限（`MAX_BREAK_ITERATIONS = 4096`）。
**新手注意**：断行是最容易写出死循环的地方（宽度算错 → 永远断不完），所以必须加上限。

代码：[GridRenderer.drawText](file:///d:/work2/test_funplay_mcp/assets/scripts/render/GridRenderer.ts#L160-L213)、[断行实现](file:///d:/work2/test_funplay_mcp/assets/scripts/render/GridRenderer.ts#L311-L397)。

## 6. 验证与调试方法论

### 6.1 三层验证金字塔

```
        ┌─────────────────────────┐
  第3层 │ 浏览器预览（真实引擎）      │  最少用，只做最终视觉确认
        ├─────────────────────────┤
  第2层 │ headless 回放（cc 替身）    │  日常主力：秒级、可断言、可批量
        ├─────────────────────────┤
  第1层 │ tsc 类型检查 + 脚本诊断     │  每次改完立刻跑
        └─────────────────────────┘
```

| 层 | 命令/工具 | 能发现什么 | 不能发现什么 |
| --- | --- | --- | --- |
| 1 | `tsc -p temp/gen-test/headless/tsconfig.json`；MCP `run_script_diagnostics` | 类型错误、拼写、导入错误 | 运行时逻辑错误 |
| 2 | `node temp/gen-test/headless/run.js` | 初始化顺序、死循环、RNG 顺序、坐标越界、文案 | 真实渲染/输入手感 |
| 3 | 浏览器 `localhost:7456` | 字体、颜色、帧率、键盘焦点 | 难以自动化、难以复现 |

### 6.2 headless 的 `cc` 替身原理

`temp/gen-test/headless` 里有一个假的 `cc` 模块，提供 `Node`、`Label`、`UITransform`、`input`、`sys.localStorage` 的空实现。于是：

- `GameRoot.onLoad()` 能真实执行；
- `GridRenderer` 的字符缓冲是真实数据；
- 把缓冲按行拼成字符串打印出来，就是 26 行 ASCII 画面。

关键点：**只有 `vendor/ecs/core/ScreenLayout` 不依赖 `cc`，这个替身才成立**。如果业务层随手 `import 'cc'`，headless 就跑不起来，你会被迫每次都开编辑器验证 —— 效率差一个数量级。

### 6.3 固定种子回归

- 地图/敌人/掉落相关改动 → 固定 `#12345`，对比改动前后的 ASCII；
- 自动游玩 → 固定一组种子（本项目用 `11111…99999` + `13579`），结果写 JSON，便于横向比较。

相关脚本：[run.js](file:///d:/work2/test_funplay_mcp/temp/gen-test/headless/run.js)、[play-one.js](file:///d:/work2/test_funplay_mcp/temp/gen-test/headless/play-one.js)、[play10.js](file:///d:/work2/test_funplay_mcp/temp/gen-test/headless/play10.js)。

### 6.4 验证死循环红线

新手最常见的自欺欺人：**同一个动作反复做，却拿不到新信息**。例如：

- 游戏跑在浏览器里，却反复截 Creator 编辑器窗口；
- 端口没开，却反复点「预览」；
- 反复跑同一条命令，看同一份旧输出。

规则：**同一验证动作连续 3 次没有新信息，就必须停下换观测面**（查运行状态、探端口、看浏览器控制台、改用 headless）。这条比任何调试技巧都重要，因为它防止你把时间烧在无效循环里。

## 8. 常见误区

1. **一上来就写 Boss**。先把「走一步、画一格」跑通，再谈战斗和关卡。
2. **把渲染和逻辑混在一起**。业务层直接 `new Label`，会导致逻辑无法脱离引擎测试。
3. **用 `Math.random()`**。一时方便，之后所有随机 bug 都无法复现。
4. **随手调整 `getUniform()` 调用顺序**。地图会在你不知情时全部变样。
5. **同步创建整屏节点**。首帧白屏，玩家以为游戏坏了。
6. **在 `update()` 里每帧整屏重绘**。帧率直接砍半。
7. **把 KeyCode 数字传进业务层**。换个平台/引擎就全废。
8. **不跟踪 Shift**。大小写键位（`h` vs `H`）直接失效。
9. **`while` 不加上限**。地图生成、断行、寻路，任何一个卡住都是「页面死了」。
10. **`lock/unlock` 不配对**。表现为「按键永久没反应」，极难查。
11. **用编辑器窗口判断游戏是否在跑**。预览在浏览器里。
12. **手改 `.scene` 的 JSON**。uuid 一错，场景直接打不开。
13. **把「HP = 栈」当成普通血量**。挨一口就以为死了，其实是背包空了。
14. **UI 坐标写死在绘制函数里**。改一次布局翻十个文件。
15. **没有固定种子回归**。改一行代码，所有地图变了却不知道哪行导致的。
